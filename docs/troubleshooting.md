# 트러블슈팅

작업하면서 막혔던 지점과 왜 지금 구조가 되었는지를 기록합니다. 같은 고민을 다시 하지 않기 위한 문서입니다.

## 명함 데이터 구조 (`entries` / `search` / `private`)

명함 한 장이 문서 세 개로 나뉘어 있습니다. 처음부터 그렇게 설계한 것이 아니라, 아래 문제를 하나씩 만나면서 지금 모양이 되었습니다.

```
cards/{id}                 공개 문서   entries, search, serialNumber, inShuffle, createdAt, uid, hasPhoto
cards/{id}/private/card    비공개      values, isPublic, password
cards/{id}/photo/data      사진        dataUrl
```

### 문제 1. 비공개로 설정한 항목이 그대로 새어나갔다

폼은 입력값을 `values: { 항목id -> 값 }` 과 `isPublic: { 항목id -> 공개여부 }` 로 들고 있습니다. 처음에는 이 두 개를 그대로 명함 문서에 저장하고, 화면에서 `isPublic` 이 `true` 인 것만 골라 보여줬습니다.

**이 방식은 동작하지 않습니다.** Firestore 보안 규칙은 문서 단위로만 허용/거부를 정할 수 있고, **필드 단위로 가릴 수 없습니다.** 명함 페이지는 누구나 열 수 있어야 하므로 문서 읽기를 허용해야 하는데, 그러면 `values` 안의 비공개 항목까지 통째로 내려갑니다. 브라우저 개발자 도구의 네트워크 탭만 열어도 보입니다.

화면에서 숨기는 것은 가리개일 뿐 접근 제어가 아닙니다.

**해결** — 저장 단계에서 나눕니다. 공개 문서에는 공개로 설정한 항목만 넣고, 입력 원본과 비밀번호는 하위 문서(`private/card`)에 두고 잠급니다. 애초에 내려가지 않으므로 화면이 무엇을 하든 상관이 없습니다.

```ts
// utils/cardUtil.ts
toCardEntries(values, isPublic); // 공개 항목만 추려서 entries 로
```

### 문제 2. `entries` 를 배열로 만든 이유

```ts
entries: [{ id: "gender", label: "성별", value: "여성" }, ...]
```

맵(`{ gender: "여성" }`)이 아니라 배열인 이유는 두 가지입니다.

- **순서를 그대로 쓴다.** 폼 정의 순서가 곧 명함에 보이는 순서입니다.
- **라벨을 그 시점으로 박제한다.** 나중에 `formFields.ts` 의 라벨을 "성별" 에서 다른 말로 바꿔도, 이미 만들어진 명함은 그때의 표기를 유지합니다. 표시용 스냅샷입니다.

라벨이 값을 담는 항목도 있습니다. SNS 는 종류가 하위 항목의 **라벨** 쪽에 들어갑니다.

```ts
{ id: "sns_id", label: "인스타그램", value: "qru_dev" }
```

추가 항목도 사용자가 고른 제목이 라벨이 됩니다. 이 둘은 나중에 검색에서 문제가 됩니다. (문제 4)

### 문제 3. `entries` 로는 조건 검색을 할 수 없다

랜덤 셔플에 "성별 · MBTI 로 좁히기" 를 붙이려다 막혔습니다.

**Firestore 는 배열 원소의 특정 필드로 거르는 질의를 지원하지 않습니다.** `array-contains` 는 원소 **전체가 정확히 일치**해야 걸리므로, `{id, label, value}` 세 개가 모두 맞아야 합니다. 라벨이 바뀌면 안 걸리고, 값만으로 찾을 수도 없습니다.

즉 `entries` 는 **보여주기에는 좋지만 찾기에는 쓸 수 없는** 구조입니다.

### 문제 4. 첫 해결책이 색인 폭발을 불렀다

처음에는 필터에 쓸 값만 따로 꺼내 두는 방식을 택했습니다.

```ts
shuffle: { enabled, key, gender, mbti }   // <- 지금은 없는 구조
```

무작위 한 장을 뽑기 위해 `key` 에 0~1 난수를 넣고, `key >= 난수` 로 범위 질의 + 정렬을 했습니다. **여기서 복합 색인이 필요해집니다.** Firestore 는 (같음 조건들 + 범위/정렬 필드) 조합마다 복합 색인을 요구합니다.

| 필터 개수 | 필요한 복합 색인 |
| --- | --- |
| 2개 (성별, MBTI) | 4조합 × 컬렉션 2개 = **8개** |
| 3개 | **16개** |
| 4개 | **32개** |

필터를 하나 늘릴 때마다 두 배가 됩니다. 항목 전체를 검색 대상으로 넓히는 것은 불가능합니다.

**해결** — 범위 질의를 버리고 **"같음" 조건만** 쓰도록 바꿨습니다. 등식만 쓰면 Firestore 가 단일 필드 색인을 합쳐서 처리하므로(index merge) **복합 색인이 하나도 필요 없습니다.** 조건을 몇 개 조합하든 색인 설정이 늘지 않습니다.

무작위 선택은 후보를 가져온 뒤 화면에서 고릅니다.

```ts
// services/card.ts
where("inShuffle", "==", true)
where(`search.${항목id}`, "==", 정규화된값)   // 조건마다 하나씩, 전부 등식
limit(CANDIDATE_LIMIT)
```

이 변경으로 `firestore.indexes.json` 을 통째로 지웠습니다.

### 문제 5. 그래서 `search` 맵이 생겼다

검색 전용으로 공개 항목을 한 번 더 저장합니다.

```ts
search: {
  gender: "여성",
  sns_id: "qru_dev",
  sns_id_label: "인스타그램",   // 라벨 쪽에 내용이 담기는 항목 (문제 2)
  hobby: "등산",
  ...
}
```

- **값과 라벨을 모두** 넣습니다. SNS 종류와 추가 항목 제목은 라벨에 있기 때문입니다.
- **정규화해서** 넣습니다. 앞뒤 공백을 없애고 소문자로 바꿉니다. `INFP` 와 `infp` 가 다르게 걸리면 안 됩니다.
- **비공개 항목은 들어가지 않습니다.** `entries` 에서 만들기 때문에 자동으로 그렇게 됩니다. 이메일을 비공개로 둔 사람은 이메일로 검색해도 나오지 않습니다.

### 겪은 버그: 드롭다운은 값을, 색인은 라벨을 갖고 있었다

필터를 붙였는데 **하나도 걸리지 않았습니다.**

- 검색 색인에는 표시용 라벨이 들어갑니다 → `search.gender = "여성"`
- 드롭다운은 폼 정의의 원본 값을 보냅니다 → `where("search.gender", "==", "female")`

영원히 안 맞습니다. 드롭다운 선택지를 만들 때 `value` 를 라벨로 바꿔서 맞췄습니다. 자유 검색어와 기준이 같아지는 이점도 있습니다.

SNS 는 한 겹 더 꼬여 있습니다. 항목 id 는 `sns` 인데 종류는 `sns_id` 의 라벨에 있으므로, 색인 키를 따로 지정합니다.

```ts
// pages/Shuffle.tsx
const FILTER_SEARCH_KEY = { sns: labelSearchKey("sns_id") };
```

### 알아둘 한계

- **부분 일치는 Firestore 가 못 합니다.** 후보를 최대 `CANDIDATE_LIMIT`(50)장 받아온 뒤 화면에서 거릅니다. 조건에 맞는 명함이 그보다 많아지면 앞의 50장만 후보가 됩니다. 명함이 쌓이면 외부 검색 서비스(Algolia 등)나 Cloud Functions 가 필요합니다.
- **같은 정보가 세 군데에 있습니다.** `entries`(표시) · `search`(검색) · `private/card`(원본). 수정 기능을 붙일 때 **세 곳을 함께 갱신**해야 합니다. 한 곳만 고치면 화면과 검색 결과가 어긋납니다.
- **자유 입력은 검색이 잘 맞지 않습니다.** "등산" / "등산하기" / "산 타기" 가 모두 다른 값입니다. 폼에 추천 칩을 둔 이유가 여기 있습니다. 표기를 모아야 검색이 쓸 만해집니다.

### 항목을 새로 추가할 때

`data/formFields.ts` 에 정의만 추가하면 나머지는 따라옵니다.

1. `entries` — 공개로 설정하면 자동으로 들어갑니다.
2. `search` — `entries` 에서 만들어지므로 자동입니다.
3. 셔플 필터 — `type: "select"` 이면 드롭다운 필터가 **자동 생성**됩니다.
4. 자유 입력이면 `suggestions` 를 넣어주세요. 표기가 모여야 검색이 됩니다.

주의할 것은 하나입니다. **하위 항목의 라벨이 내용을 담는 구조**(SNS 같은)를 새로 만든다면, `FILTER_SEARCH_KEY` 에 매핑을 추가해야 필터가 맞습니다.
